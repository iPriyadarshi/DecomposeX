The Algorithm

Computing L, D and U

LDU factorization is Gaussian elimination with bookkeeping. This page shows where each factor comes from, what to do when a pivot is zero, and how the whole thing fits in a page of pseudocode.

The central observation

Elimination clears the entries below a pivot by subtracting multiples of the pivot row. The key insight is that each such row operation is invertible, and its inverse is recorded by a single number: the multiplier that was used.

At stage k, with pivot akk, the operation applied to row i below it is

Ri ← Ri − mik · Rk,    where   mik = aik ⁄ akk.

To undo it you add the same multiple back. So if you keep every mik, you have kept enough information to rebuild the original matrix from the reduced one, and the natural place to keep them is exactly the position they cleared. That array of multipliers is L.

Where each factor comes from
L
The multipliers. ℓik = mik, stored in the very position that the operation zeroed out. The diagonal is 1 because a row is never scaled against itself.
Û
What elimination leaves behind: an upper-triangular matrix whose diagonal entries are the pivots actually used.
D
Those pivots, lifted off the diagonal of Û.
U
Û with each row divided by its own pivot, which leaves 1s on the diagonal.

The same thing as a matrix product

Formally, clearing column k is left-multiplication by an elementary matrix Ek: the identity with the multipliers placed, negated, below the diagonal in column k. Elimination is therefore

En−1 ⋯ E2 E1 A = Û

and rearranging gives the factorization directly:

A = E1−1 E2−1 ⋯ En−1−1 Û = L Û

The product of those inverses collapses into a single unit lower-triangular matrix whose entries are just the multipliers, un-negated, which is why L can be filled in as you go, with no extra multiplication.

Handling a zero pivot

Everything above assumed akk ≠ 0. A correct implementation has to decide what to do when it is not, and there are exactly three situations. Getting this wrong is the most common bug in hand-written LDU code: dividing by zero silently yields Infinity or NaN, which then contaminates every later entry.

Situation at stage kCorrect responseResult
Pivot is zero, but some row below has a non-zero entry in column k Swap that row up and continue P·A = L·D·U
Column k is zero from row k down, and row k is also empty to the right Set dk = 0, take row k of U to be ek, continue Factorization holds, but U is not unique
Column k is zero from row k down, but row k is not empty Report that no LDU factorization exists Only the LU form A = L·Û is available
Why the third case is genuinely impossible

If dk = 0 then row k of D·U is zero, because that row of the product is dk times row k of U. Row k of L·D·U is then determined entirely by the rows above it. If elimination has left something non-zero in row k, no choice of U can reproduce it. The obstruction is structural, not numerical.

Partial pivoting, and why exact arithmetic changes the picture

Numerical libraries do not wait for a pivot to be exactly zero. They always swap the largest available entry into the pivot position, because dividing by a small number amplifies rounding error. That strategy is called partial pivoting, and it is why PA = LU is the default in LAPACK, NumPy and MATLAB.

With exact rational arithmetic there is no rounding error to amplify, so partial pivoting buys no accuracy: every strategy gives an exactly correct answer. What it changes is which correct answer you get, since a different P means different L, D and U. That is why the calculator defaults to swapping only when forced: it keeps P equal to the identity whenever the matrix allows, which is the form a textbook expects.

Pseudocode

The whole method, with the pivot handling written out rather than assumed away. Indices are 1-based.

Phase 1: elimination
// Input:  A, an n×n matrix
// Output: L unit lower triangular, Û upper triangular,
//         perm (the row order), swaps (a count)

L ← identity(n)
Û ← copy(A)
perm ← [1, 2, …, n]
swaps ← 0

for k ← 1 to n:

    // --- choose a pivot ---
    if Û[k][k] = 0:
        r ← smallest index > k with Û[r][k] ≠ 0, or none
        if r exists:
            swap rows k and r of Û
            swap L[k][1.k−1] with L[r][1.k−1]   // multipliers travel with their rows
            swap perm[k] and perm[r]
            swaps ← swaps + 1
        else:
            // column k is empty below the diagonal: nothing to do,
            // and d_k will be 0. Phase 2 decides whether that is fatal.
            continue

    // --- eliminate below the pivot ---
    for i ← k+1 to n:
        if Û[i][k] = 0:
            L[i][k] ← 0                    // already clear, no work
            continue
        m ← Û[i][k] / Û[k][k]
        L[i][k] ← m
        for j ← k to n:
            Û[i][j] ← Û[i][j] − m · Û[k][j]
        Û[i][k] ← 0                        // exact by construction; assign it rather than
                                              // trusting the subtraction to land on zero
Phase 2: split Û into D · U
D ← zeros(n, n)
U ← identity(n)
failed ← none

for k ← 1 to n:
    d ← Û[k][k]
    D[k][k] ← d

    if d = 0:
        if row k of Û is entirely zero:
            U[k][*] ← e_k          // any unit-triangular row works; pick the simplest
        else:
            failed ← k             // no LDU factorization exists
        continue

    for j ← k to n:
        U[k][j] ← Û[k][j] / d
    U[k][k] ← 1                    // exact by construction

if failed ≠ none: report failure, return L and Û only
else: return L, D, U, perm, swaps
The detail that catches everyone

When rows k and r are swapped, the multipliers already stored in L must be swapped too, but only those in columns 1 … k−1. Those entries belong to rows of the original matrix, and if a row moves, the record of how it was reduced moves with it. Swapping the whole row of L (including the diagonal 1) breaks the unit structure; swapping nothing gives a product that is silently wrong.

Always verify

The factorization is cheap to check and the check is completely independent of the algorithm: just multiply the factors back and compare. It takes O(n³) operations, the same order as the factorization itself, and it catches every class of bug discussed above.

Verification
assert L · D · U = P · A     // entry by entry
assert L · Û     = P · A     // the LU form, valid even when LDU is not
assert det A = (−1)^swaps · d₁ · d₂ ⋯ dₙ

In exact arithmetic these are literal equalities, which is what the calculator reports on its Verification tab. In floating point you would instead check that the residual is small relative to the size of the entries, and “small” is a judgement call, which is exactly the ambiguity exact arithmetic removes.

Cost

Stage k computes n − k multipliers and updates an (n − k) × (n − k + 1) block. Summing over all stages:

∑k=1n (n − k)2 ≈ n3 ⁄ 3   multiply–add pairs
TaskCostNote
Phase 1: elimination~n³/3Dominates everything else
Phase 2: the D/U split~n²/2 divisionsNegligible
Solving one system afterwards~n²Two substitutions plus n divisions
Determinant from the factorsnMultiply the pivots, apply the sign
Full inverse~n³n substitution pairs, reusing one factorization

This is the payoff that motivates the whole exercise: the expensive part depends only on A. Factor once at n³/3, then answer each new right-hand side for n². For n = 1000 that is the difference between a third of a billion operations and a million.

Why this site does not use floating point

Every implementation decision above assumed you can answer the question “is this pivot zero?”. In floating point you often cannot.

Doubles store about 15–16 significant decimal digits. Subtracting two nearly equal numbers destroys most of them, and elimination does exactly that, repeatedly. A pivot that is mathematically zero typically emerges as something like 4.9e-17: not zero, so the test for a zero pivot passes, and the algorithm happily divides by it. The multipliers explode, and the reported factors are meaningless while looking perfectly respectable to two decimal places.

The failure takes two forms, and the demonstration below computes both for real.

Failure 1: the loud one

When a pivot does come out as exactly 0.0, dividing by it gives Infinity, and the next subtraction turns that into NaN. Every later entry is poisoned. An implementation that does not test the pivot before dividing produces a grid of NaN, and if it formats output with something like toFixed(2), that grid can still look like a plausible answer.

Failure 2: the quiet one

Worse is when cancellation leaves a pivot that is nearly zero rather than zero. The test pivot === 0 passes, no swap is triggered, no warning is raised, and the algorithm reports a singular matrix as invertible, with a determinant of around 10−16 instead of exactly 0.

The alternative is a tolerance: treat anything below, say, 10−12 as zero. That works in practice for well-scaled problems, but it is a heuristic: multiply the matrix by 10−10 and the tolerance misfires. For a teaching tool that is the wrong trade, so DecomposeX stores every value as a ratio of arbitrary-precision integers:

The representation
class Fraction:
    n: BigInt        // numerator, carries the sign
    d: BigInt        // denominator, always > 0
    // invariant: gcd(|n|, d) = 1  (always in lowest terms)

Addition, subtraction, multiplication and division of rationals are closed operations, so nothing is ever approximated. The cost is that numerators and denominators grow: for a 10×10 matrix they can reach dozens of digits, which is a fine price for a tool whose job is to be right and to be understood.
